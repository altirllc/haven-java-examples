# loom

Haven **agentic** tenant application in Java, generated from `scaffold/java/agent`. loom **supervises another app's automated decisions**: it polls [Anvil](../../haven-anvil/), opens a **case** per work item with a deadline, and has its own agent judge whether Anvil's triage decision was defensible — **agree**, **dispute** (which flags the item back to Anvil so a human sees it) or **escalate**. A case nobody settles before its deadline **lapses**. Escalation and lapse both raise a notification through Dispatch (fn-notifications).

Two long-lived daemons in `jobs/`, deliberately separate — different failure modes, different cadences: `loom-ingest` polls Anvil, and the agent daemon sweeps open cases and **signals that case's `processCase` workflow** with a review, exactly as a human reviewer would. The per-case workflow and the agent stay decoupled; either can drive it. A secondary chat endpoint talks to the same agent. Semantic memory is Postgres-backed.

**loom builds on top of Anvil and never modifies it.** Everything it knows about an item arrives over Anvil's public REST surface; the only thing it writes back is a flag.

Runs inside a tenant vCluster; platform services (Temporal, SeaweedFS S3, PostgreSQL + pgvector, MongoDB), secrets, routing, and deployment come from the platform — see the root CLAUDE.md.

## Critical

CRITICAL - Records — every Postgres table lives in the `loom` schema, including Liquibase's own DATABASECHANGELOG. Never write to `public` or another app's schema. The datasource pins `search_path` (`spring.datasource.hikari.schema`) so this holds for libraries that create their own tables; the schema itself is created by `MigrationConfig` under the migration's advisory lock.
CRITICAL - Workflows — every Temporal `workflowId` is prefixed `loom-`. The task queue routes work to the right worker; the ID prefix prevents collisions in the tenant's shared namespace.
CRITICAL - Storage — every S3 object key is prefixed `loom/` inside the tenant bucket. Never write objects to the bucket root.
CRITICAL - Maven's compile scope is TRANSITIVE — a dependency added to `domain` or `contracts` lands on the workflow classpath with no compile error anywhere. The enforcer rule in `workflows/pom.xml` is what holds the line; never weaken it, and never add a dependency to `domain`/`contracts` without knowing it reaches `workflows`.

## The determinism fence — read this before touching `workflows/`

Temporal replays workflow code from the beginning to recover, so it **must be deterministic**: no IO, no clock, no randomness, no threads. **Temporal's Java SDK has no workflow sandbox** — nothing stops you, and a violation passes every test and then corrupts on replay in production weeks later.

So the guardrail is built, in three layers:

1. **The module graph is the fence.** `workflows` depends on `domain` and `contracts` only. Hibernate, Spring, Spring AI, S3 and the Temporal *client* are not on its classpath — calling them does not compile. This is why `contracts` (interfaces only) exists separately from `orchestration` (the Temporal client).
2. **ArchUnit covers what the graph cannot.** `java.base` is on every classpath, so nothing stops `Instant.now()` or `UUID.randomUUID()`. `WorkflowDeterminismTest` bans them. Use `Workflow.currentTimeMillis()`, `Workflow.randomUUID()`, `Workflow.newRandom()`, `Workflow.sleep()`. A second rule forbids implementing a `@WorkflowInterface` outside `workflows` — otherwise an engineer who hits the fence could "fix" it by putting the workflow in `jobs`, where the cases service IS on the classpath, and silently disable everything.
3. **The enforcer rule** (`verify-determinism-fence` in `workflows/pom.xml`) asserts the resolved dependency tree on every build. The failure mode it catches: Maven's compile scope is transitive, so a persistence-flavored dependency added to `domain` flows `domain` → `contracts` → `workflows` with **no compile error anywhere**. `bannedDependencies` fails the build instead — test scope exempt, main scopes banned.

**Do not use `temporal-spring-boot-starter` in `workflows`.** Its `@WorkflowImpl` annotation ships inside the starter, so annotating an implementation drags Spring onto the workflow classpath. `jobs` registers workflow classes explicitly (`WorkerConfig`) instead — about 20 lines.

## Structure

Eight Maven modules under one parent POM. The count is a fixed cost paid once: adding a table touches 3 existing modules and **zero** build files.

```
backend/       the Maven build — all JVM modules and machinery (pom.xml = the parent)
frontend/      the React UI (standalone npm project)
bundle/        Haven deployment manifests

Inside backend/:

domain         records + enums (Case, CaseState, ReviewAction, AnvilDecision, …). Nothing that does IO.
contracts      the Temporal SURFACE — @ActivityInterface + @WorkflowInterface. Interfaces only.
workflows      workflow IMPLS. FENCED — see above.
orchestration  the Temporal CLIENT: WorkflowClient, starting + signalling.
persistence    Liquibase changelogs, JPA entities/repositories, CaseService (the sole gate), Mongo wiring.
agent          Spring AI agent + its four tools. Shared by both deployables.
api    (app)   REST (3000) + MCP (3001), identity, S3.        → ghcr.io/…/loom-api
jobs   (app)   worker + activity impls + both daemons +      → ghcr.io/…/loom-jobs
               the Anvil client and the Dispatch notifier.
```

**Growth rule:** Maven modules exist for **deployables** and for **the determinism fence** — nothing else. When `persistence` or `api` grows past ~5 feature areas, partition them *internally* (Spring Modulith is the natural tool), not by adding Maven modules. Otherwise the 40-table app becomes a 47-module build.

## Conventions

- **Config**: `@ConfigurationProperties` records + `@Validated`, validated at boot — a missing value kills the process rather than surfacing at the first request. Never read env directly. In a cell every value arrives as an env var from the bundle; locally the `local` profile (`application-local.yaml`, gitignored) supplies them. The bundle sets `SPRING_PROFILES_ACTIVE=production`, which `IdentityResolver` keys on — production must never fabricate a user.
- **Persistence**: `CaseService` is THE cases API and the only caller of the JPA layer (`haven.loom.persistence.jpa` — ArchUnit enforces it, plus a rule that `jakarta.persistence`/`org.springframework.data` never appear outside `persistence`). Every actor — REST, MCP, agent tools, Temporal activities — goes through it. Liquibase changelogs (`db/changelog/`, formatted SQL) are the single DDL source of truth; Hibernate runs `ddl-auto: validate` so entity/changelog drift kills the boot, and `CaseServiceTest` exercises that same path against real Postgres (Testcontainers), which makes drift fail the BUILD. Never edit a shipped changeset — add a new file and `include` it. Orchestration is NOT in the service: starting workflows and signalling live in `orchestration`.
- **Metering**: `UsageService` is the plan gate and `loom.usage_events` (append-only, deterministic id `<caseId>:cases`) is both the record and the enforcer. **The metered unit is `cases`**, single-sourced from `UsageService.UNIT_CASES` — the ledger, the `haven_usage` gauge tag and the `unit` in `service.json`'s plans block must agree, and a second string literal is how they stop agreeing. `CaseService.openCase` calls `usage.consumeCase(id)` first, inside the same `@Transactional`, under a `pg_advisory_xact_lock` whose key is the 32-bit FNV-1a of the app name (`lockKey("loom")`) — advisory locks are database-scoped, and apps sharing the tenant database must not collide on one — refuse-before-write: the unit is known upfront, so on the `free` plan opening a case past the allowance throws `PlanLimitReachedException` and nothing commits; `paid` continues and the excess is what gets billed. Only opening a case meters — reviews and reads consume nothing. Ingest treats a spent allowance as a normal condition: it stops opening cases and **keeps refreshing the ones it already has**. Config is `PlanProperties` (`PLAN` free|paid + `PLAN_FREE_CASES`, both from the `{appname}-config` ConfigMap — the platform projects the allowance into it from the `plans` block in `service.json`, so enforcement and display share one source; boot-fatal when missing). REST renders the refusal as 402 `{error, code: "PLAN_LIMIT_REACHED"}` via `CaseController`'s `@ExceptionHandler`; the MCP tool rethrows it as `IllegalStateException("PLAN_LIMIT_REACHED: …")` — the don't-retry convention for calling agents. A workflow-start failure after opening unwinds via `cases.discardCase(id)` (usage row + logs + case in one transaction); a failed unwind warn-logs a possibly leaked unit. `UsageMetrics` (jobs) exports the `haven_usage{unit="cases"}` gauge from the ledger on the auto-scraped `management` port, serving the last-known value when a read fails — a scrape must never fail.
- **Entities carry jsonb as `String`** (`@JdbcTypeCode(SqlTypes.JSON)`): Jackson (de)serialization is `CaseService`'s job, so Hibernate needs no format mapper and no object-graph state. Entities are relationship-free (raw FK columns, no `@ManyToOne`) — the audit log is append-only and lazy-loading state would buy nothing. Server-side jsonb merges (`coalesce(x,'{}'::jsonb) || patch`) stay native `@Modifying` queries in the repositories.
- **Ids are `UUID`**, not text: 16 bytes, proper indexing. It serialises to a JSON string, so the UI is unaffected.
- **Timestamps**: `CaseService.now()` is the single clock — UTC, microsecond-truncated, so an in-memory record equals its own timestamptz round-trip (Postgres normalizes to UTC and stores micros).
- **Wire contract is frozen**: the React UI (`frontend/src/api/client.ts`) reads these names verbatim. Cases/logs use snake_case (`created_at`, `case_id`); the agent endpoints use camelCase (`lastActionAt`). No global naming strategy covers both — hence `@JsonProperty` on the domain records.
- **MongoDB is wired, deliberately unused.** The platform provisions Mongo in every tenant; the bundle injects `MONGODB_URI` and `MongoConnectionCheck` (in `persistence`) pings it at boot — a bad URI kills the process, and `MongoUnreachableFailureAnalyzer` renders it cleanly. No collections, no seeds, no queries: the first document feature starts from Spring Data repositories in `haven.loom.persistence.mongo` — and from a connection that already works. Gotcha 1: Boot 4 renamed the driver keys to `spring.mongodb.*` — the old `spring.data.mongodb.uri` is deprecation-level *error* and silently unbound, and the driver's `localhost/test` default masks the mistake locally. Gotcha 2: locally, `spring-boot-docker-compose` DERIVES the Mongo connection from the compose service and overrides the properties — the database name comes from the service's `MONGO_INITDB_DATABASE` env, not from any yaml.
- **Agent**: four tools — `get-case`, `list-cases`, `agent-status` (read) and `review-case` (act, named by `AgentDefinition.ACT_TOOL` so the read/act split cannot drift from the tool that exists). `review-case` records the verdict then **signals the workflow**; it never writes state. `CaseTools.describe` renders a deadline as **time left in words** (`in 2h 41m`, `PASSED 1h 12m ago`), never a timestamp: date arithmetic is what models get quietly wrong, and "little time remains" is the escalate trigger. **Doing nothing is a legitimate sweep outcome** — an item Anvil has not decided yet has nothing to judge, and the agent must not invent a verdict. `AgentDefinition` reads its tool catalogue off the live `@Tool` annotations by reflection, so `GET /api/agent/config` cannot drift from what actually runs. The build passes `-parameters` (via spring-boot-starter-parent) — Spring AI derives tool argument names from reflection, so removing it breaks tool calling.
- **The decision trace is a CONTRACT, not a log line.** `frontend/src/api/client.ts` defines `AgentTrace`, and `ReviewTrace.tsx` calls `trace.steps.map` and `trace.remembered.map` — a missing key throws and takes the case page down rather than degrading. If you change what `AgentActivitiesImpl.trace()` emits, check it against that interface. A green API test will not catch this; the UI is the only judge.
  **Known shallowness:** `steps` holds the final round only — Spring AI executes the tool loop internally, so intermediate rounds are not observable. Capturing them means disabling internal tool execution and driving the loop by hand. **Never pad `steps` or `toolResults` with invented content** — the trace teaches how the agent reasoned, and a plausible fabrication teaches a lie.
- **Models**: everything goes through the platform **model gateway** (LiteLLM in `haven-models`, reached via the `models-litellm` mirror) with the tenant's virtual key from `tenant-models-secret` — the app carries no provider credentials. Auth is just `spring.ai.openai.api-key`; model names are gateway aliases naming the role, not the vendor model behind it (`chat-with-haven`, `text-embedding-1024`). `ModelsGatewayConfig` probes `GET /v1/models` at boot so a missing or rejected key kills the process — the same fail-fast the app applies to Postgres and Temporal (`ModelsGatewayFailureAnalyzer` renders it cleanly).
- **Two databases, both declared explicitly** (`VectorStoreConfig`): the app database is `@Primary`, the pgvector `vectors` database is a named second datasource for the vector store only. This is load-bearing: the moment any `DataSource` bean exists, Boot's autoconfiguration backs off and `spring.datasource.*` is silently ignored — a lone vectors bean makes the ENTIRE app (Liquibase, JPA, chat memory) write to the vectors database while every API test stays green. If you add a datasource, keep the primary explicit. PgVector's autoconfiguration stays excluded for the same reason. All DDL is Liquibase-owned and HAND-DRIVEN through `LockedLiquibase`: the primary via `MigrationConfig` (persistence), the vectors DB via `vectorsLiquibase` (VectorStoreConfig); the store's and chat-memory's own initializers stay off. Boot-time DB races are absorbed by Hikari (`initialization-fail-timeout: 30s`).
- **Boot's Liquibase autoconfiguration is absent by construction**: the build depends on plain `liquibase-core`, never `spring-boot-starter-liquibase`, so `LiquibaseAutoConfiguration` is not on the classpath and there is no `spring.liquibase.*` config to drift. The reason it cannot be used: api and jobs boot together in the same pod, and on a fresh tenant EVERY bootstrap step races: Liquibase's lock table cannot serialize its own creation (`duplicate key ... pg_type_typname_nsp_index`), and even `CREATE SCHEMA IF NOT EXISTS` collides in Postgres when two sessions run it concurrently (`pg_namespace_nspname_index` — which is also why schema creation must NOT live in Hikari's connection-init-sql: that fires at pool startup, outside any lock). `LockedLiquibase` therefore does schema creation AND the changelog under one `pg_advisory_lock`, and `MigrationConfig` always migrates through the pool. `EntityManagerFactoryDependsOnPostProcessor` keeps Hibernate's validate ordered after the migration.
- **Two ports, one process**: the edge leaves `/mcp` **ungated** and routes it to a dedicated `loom-mcp` service, so that listener must expose nothing else — otherwise `/mcp/loom/api/cases` reaches the REST API unauthenticated after Traefik strips the prefix. `ApiApplication` uses parent/child contexts: the COMPONENT scan is what isolates. A second Tomcat connector does **not** work (spring-boot#50355). Note `SpringApplicationBuilder.parent(...)` returns the *original* builder — pass the parent to the constructor. Corollary: `spring-boot:run` delivers the `local` profile as the `SPRING_PROFILES_ACTIVE` env var, because only the process environment reaches every context in the chain — plugin `<profiles>`/program args do not.
- **Anvil is upstream, and loom is a guest in it.** `AnvilClient` lives in `jobs` — only the worker talks to Anvil, which keeps an HTTP client off the api and workflow classpaths. A poll makes exactly TWO calls: `GET /api/items` and `GET /api/agent/activity`. The activity feed carries the triager's rationale for every item at once, which is what avoids an N+1 per-item log fetch; the feed is newest-first, so the FIRST entry seen for an item wins. The only write is `flagItem` — **flag, not reject**: loom supervises, it does not overrule, and Anvil's flag is what puts the item back in front of a human. A 409 from it means "already resolved" and is an OUTCOME, not a retryable error. **loom deliberately sends only a bearer token and never `X-Auth-Request-*`.** Anvil resolves its caller from those headers and any in-cluster neighbour can forge them (`haven/SECURITY-edge-header-trust.md`); loom refuses to build on that, so in a cell these calls 403 until the platform gives an app a way to prove who it is. `refuseLoudly` says exactly that on a 401/403 rather than retrying into a wall.
- **The SLA deadline is fixed ONCE, at open.** `ProcessCaseWorkflowImpl` computes `deadline = Workflow.currentTimeMillis() + sla` before the loop and sleeps the *remaining* time on every pass. Recomputing it per iteration is the obvious-looking change and is a bug: a case that is disputed repeatedly would never lapse, so the failure loom exists to catch — nobody ever settled it — becomes the one failure it cannot see. A regression test pins this. Lapse is the more important of the two notifications for the same reason: an escalation means someone noticed, a lapse means nobody did.
- **Notifications go through Dispatch (fn-notifications), on escalate and on lapse.** The division of labour is the whole design and is documented on `DispatchProperties`: **loom owns its vocabulary** — the event name, the routing rule and the template — and registers all of it itself at boot, idempotently. **The tenant owns its taxonomy and its people** — category, subcategory, recipients — and loom will NOT invent them: when `DispatchProperties.missing()` returns a reason, the case timeline gets a `notify-skipped` row carrying that reason, never silence. Audit rows are `notified` / `notify-skipped` / `notify-failed`, and a failed push-back writes `push-back-failed` — the timeline must never imply Anvil was told when it was not. Three things learned only from a live stack: (1) **a rule is acknowledged before it is live** — an event published straight after creating its rule gets no reply at all, hence `requestWhenRuleIsLive`; (2) **a rule's identity is its id, not its `eventName`** — registering a new id for the same event leaves the old rule live and the tenant gets two notifications per case, which is why the ids in `dispatch.*` are fixed defaults and must stay stable; (3) two `Dispatch` instances share the `loom-admin` consumer group and steal each other's replies, so **jobs must run a single replica**. `dispatch.enabled` defaults to false: a tenant without Dispatch is not broken.
- **fn-notifications cannot accept its first rule unaided.** Creating a rule is itself an event, and routing that event needs a rule — so one `CREATE_RULE` row has to be seeded directly into its Mongo before the service starts (it reads rules at boot; a row inserted later stays invisible until restart). That is tenant provisioning, not application logic, and loom does not reach into a neighbour's database to do it. The compose stack seeds it (`dispatch-seed`); in a cell it belongs to the dispatch bundle, which currently appears to lack the step.
- **Logging**: `logging.structured.format.console=ecs`. One property; no encoder library, no logback XML.
- **Health & metrics**: Actuator on both apps. Liveness carries no dependency checks; readiness is `readinessState,db` ONLY — never secondary datastores (one replica: unready = full outage; a Mongo blip must degrade Mongo features, not the app). The traffic-less jobs worker gets liveness + startup probes only — pod readiness is ANDed across containers, so a worker readiness check would unplug api traffic. The MCP context excludes actuator via an `exclude=*` default property in `ApiApplication` (an include there would lose to the yaml's). jobs serves actuator on `MANAGEMENT_PORT` 3002; the bundle names that port `management`, which the platform Prometheus auto-scrapes at `/actuator/prometheus`.

## Commands

| | Build | Check | Dev |
|---|---|---|---|
| all | `backend/mvnw -f backend/pom.xml verify` | `backend/mvnw -f backend/pom.xml -DskipTests verify` | `backend/mvnw -f backend/pom.xml -pl api spring-boot:run` / `-pl jobs spring-boot:run` |

`verify` runs the ArchUnit determinism rules and the enforcer classpath fence. Integration tests need Docker (Testcontainers); on Colima, export `DOCKER_HOST=unix://$HOME/.colima/default/docker.sock` and `TESTCONTAINERS_DOCKER_SOCKET_OVERRIDE=/var/run/docker.sock`.

```bash
backend/mvnw -f backend/pom.xml -DskipTests install       # once, and after cross-module changes
backend/mvnw -f backend/pom.xml -pl api spring-boot:run   # REST 3000, MCP 3001 — starts the compose stack itself
backend/mvnw -f backend/pom.xml -pl jobs spring-boot:run  # worker + agent daemon
npm --prefix frontend run dev                             # UI on 5173, proxying to 3000
./dev.sh                      # or: all of the above via concurrently
```

`spring-boot:run` activates the `local` profile and manages the backing services
via `spring-boot-docker-compose` (start-only: the stack survives app restarts;
`docker compose down` stops it). It resolves sibling modules from the local
repository — run the `install` after cross-module changes.

## Docker

The JVM images build from `backend/` (they need every module).

```bash
docker build -f backend/api/Dockerfile -t loom-api backend/
docker build -f backend/jobs/Dockerfile -t loom-jobs backend/
docker build -f frontend/Dockerfile -t loom-ui frontend/
```

**Not jlink, and not GraalVM native** — same reason for both. Each trims the runtime by assuming it knows which classes load, and each is wrong in ways you only find at runtime: this app's own dependencies already need modules like `java.desktop` (Spring's binder) that are never statically referenced. The dependencies are ~162MB regardless, so trimming the JRE buys little against a permanent tax on everyone who adds a library.
